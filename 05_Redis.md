# Redis - Руководство для технического интервью

> 💡 **Как объяснить Redis на интервью за 30 секунд:**
> "Redis — это in-memory база данных, работающая в оперативной памяти. Благодаря этому она невероятно быстрая — операции выполняются за микросекунды. Используется для кеширования, сессий пользователей, очередей и rate-limiting."

---

## 1. Базовые операции: GET, SET, TTL

### 🎯 Что спрашивают на интервью
> "Что такое Redis и для чего используется?"

### Простое объяснение
Redis — это как супербыстрый блокнот в оперативной памяти. Записал — мгновенно прочитал. Но помни: если выключить свет (сервер), блокнот очистится (если не настроена персистентность).

### Ключевые команды

```bash
# Записать значение
SET user:1:name "Иван"

# Прочитать
GET user:1:name  # "Иван"

# Записать с временем жизни (TTL)
SET session:abc "data" EX 3600  # Исчезнет через 1 час

# Проверить сколько осталось жить
TTL session:abc  # Секунды до удаления

# Атомарный инкремент (потокобезопасно!)
INCR page:views  # Было 5, стало 6
```

### Зачем TTL?
- **Кеширование**: данные устаревают, не засоряем память
- **Сессии**: автоматический logout
- **Rate limiting**: счётчик запросов сбрасывается

### 📝 Фраза для интервью
> "Redis хранит данные в памяти, поэтому операции выполняются за микросекунды. Основные операции GET/SET, можно задать TTL для автоматического удаления. INCR атомарен, что важно для счётчиков в многопоточной среде."

## 2. Структуры данных

### 🎯 Что спрашивают
> "Какие структуры данных поддерживает Redis?"

### Главное преимущество Redis
Redis — это **не просто key-value**! Он поддерживает сложные структуры:

### Strings (строки)
```bash
SET name "Иван"
INCR counter  # Атомарный инкремент
```
**Use case**: кеш, счётчики, сессии

### Lists (списки)
```bash
RPUSH queue "task1"  # Добавить в конец
LPOP queue           # Забрать из начала
BLPOP queue 0        # Ждать элемент (блокирующе)
```
**Use case**: очереди задач, лента новостей

### Sets (множества)
```bash
SADD online:users "user1" "user2"
SISMEMBER online:users "user1"  # Проверка членства O(1)!
SINTER friends:user1 friends:user2  # Общие друзья
```
**Use case**: уникальные значения, теги, общие друзья

### Sorted Sets (сортированные множества)
```bash
ZADD leaderboard 100 "player1"
ZREVRANGE leaderboard 0 9  # Топ-10
ZINCRBY leaderboard 10 "player1"  # +10 очков
```
**Use case**: рейтинги, таймлайны, приоритетные очереди

### Hashes (хеши)
```bash
HSET user:1 name "Иван" email "ivan@mail.ru" age 25
HGET user:1 name
HGETALL user:1
```
**Use case**: объекты (юзеры, товары), сессии

### 📝 Фраза для интервью
> "Redis поддерживает не только строки, но и списки, множества, сортированные множества и хеши. Это позволяет решать сложные задачи: очереди через списки, рейтинги через sorted sets, уникальные посетители через sets."

## 3. Pipeline и Pub/Sub

### 🎯 Что спрашивают
> "Как оптимизировать взаимодействие с Redis?"

### Pipeline — батчинг запросов

**Проблема**: Каждая команда — это сетевой запрос (round-trip).

```python
# ❌ Плохо: 1000 сетевых запросов
for i in range(1000):
    redis.set(f'key:{i}', i)

# ✅ Хорошо: 1 сетевой запрос
pipe = redis.pipeline()
for i in range(1000):
    pipe.set(f'key:{i}', i)
pipe.execute()  # Отправляем всё разом
```

**Результат**: 10-100x ускорение!

### Pub/Sub — подписка на события

```python
# Publisher (отправляет)
redis.publish('notifications', '{"user": 1, "message": "Новый заказ"}')

# Subscriber (получает)
pubsub = redis.pubsub()
pubsub.subscribe('notifications')
for message in pubsub.listen():
    print(message)  # Получаем в реальном времени
```

**Use case**: real-time уведомления, чаты, обновления

### 📝 Фраза для интервью
> "Pipeline позволяет отправить несколько команд за один сетевой запрос, ускоряя работу в десятки раз. Pub/Sub — для real-time messaging, но без гарантии доставки. Для надёжных очередей лучше использовать Redis Streams или RabbitMQ."

## 4. Кеширование — главный use case

### 🎯 Что спрашивают
> "Как реализовать кеширование с Redis?"

### Паттерн Cache-Aside

```python
def get_user(user_id):
    # 1. Проверяем кеш
    cached = redis.get(f'user:{user_id}')
    if cached:
        return json.loads(cached)
    
    # 2. Cache miss — идём в базу
    user = database.query(f"SELECT * FROM users WHERE id = {user_id}")
    
    # 3. Сохраняем в кеш на 1 час
    redis.setex(f'user:{user_id}', 3600, json.dumps(user))
    
    return user
```

### Проблема Cache Stampede
Когда кеш истекает, 1000 запросов одновременно идут в базу.

**Решение — блокировка**:
```python
def get_user_safe(user_id):
    cached = redis.get(f'user:{user_id}')
    if cached:
        return json.loads(cached)
    
    # Пробуем захватить блокировку
    if redis.set(f'lock:user:{user_id}', '1', nx=True, ex=5):
        user = database.query(user_id)
        redis.setex(f'user:{user_id}', 3600, json.dumps(user))
        redis.delete(f'lock:user:{user_id}')
        return user
    else:
        time.sleep(0.05)  # Ждём пока другой заполнит кеш
        return get_user_safe(user_id)
```

### 📝 Фраза для интервью
> "Типичный паттерн — cache-aside: проверяем кеш, при miss идём в базу и сохраняем результат с TTL. Важно помнить про cache stampede — когда кеш истекает, можно перегрузить базу. Решается блокировкой или вероятностным обновлением."

## 5. KEYS vs SCAN — важно для production!

### 🎯 Что спрашивают
> "Как найти все ключи по паттерну?"

### ⚠️ НИКОГДА не используйте KEYS в production!

```bash
# ❌ ОПАСНО: блокирует Redis на всё время выполнения
KEYS user:*  # Если миллионы ключей — Redis "замёрзнет"

# ✅ Безопасно: итеративное сканирование
SCAN 0 MATCH user:* COUNT 100
```

```python
# Python — правильный способ
for key in redis.scan_iter(match='user:*', count=100):
    process(key)
```

### Почему SCAN безопасен?
- Возвращает по частям (курсор)
- Не блокирует другие операции
- Может быть медленнее, но не "убивает" Redis

### 📝 Фраза для интервью
> "KEYS блокирует Redis на всё время выполнения — на production с миллионами ключей это катастрофа. Всегда использую SCAN, который работает итеративно и не блокирует сервер."

## 6. Persistence — сохранение данных

### 🎯 Что спрашивают
> "Что будет с данными Redis при перезапуске?"

### Два механизма

| Механизм | Как работает | Потеря данных |
|----------|-------------|---------------|
| **RDB** | Снимки (снапшоты) по расписанию | До нескольких минут |
| **AOF** | Журнал всех операций | До 1 секунды |

### RDB (Redis Database)
```bash
# redis.conf
save 900 1      # Снимок если 1 изменение за 15 мин
save 60 10000   # Снимок если 10000 изменений за 1 мин
```
✅ Компактный, быстрый бэкап
❌ Можно потерять данные

### AOF (Append Only File)
```bash
# redis.conf
appendonly yes
appendfsync everysec  # Синхронизация каждую секунду
```
✅ Минимальная потеря (1 сек)
❌ Файл больше, медленнее

### 📝 Фраза для интервью
> "По умолчанию Redis хранит всё в памяти. RDB делает периодические снимки — можно потерять данные между снимками. AOF записывает каждую операцию — потеря максимум 1 секунда. Для production обычно используют оба."

## 7. High Availability — Redis Sentinel

### 🎯 Что спрашивают
> "Как обеспечить отказоустойчивость Redis?"

### Проблема
Один сервер Redis — единая точка отказа.

### Решение — Redis Sentinel

```
┌───────────┐   ┌───────────┐   ┌───────────┐
│ Sentinel  │   │ Sentinel  │   │ Sentinel  │
└─────┬─────┘   └─────┬─────┘   └─────┬─────┘
      │               │               │
      └───────────────┼───────────────┘
                      │ мониторинг
              ┌───────▼───────┐
              │    Master     │
              └───────┬───────┘
        ┌─────────────┼─────────────┐
┌───────▼───────┐           ┌───────▼───────┐
│   Replica 1   │           │   Replica 2   │
└───────────────┘           └───────────────┘
```

**Что делает Sentinel:**
1. Мониторит master и реплики
2. При падении master — автоматически выбирает новый
3. Уведомляет приложения о новом master

### 📝 Фраза для интервью
> "Redis Sentinel обеспечивает high availability: мониторит master и реплики, при отказе master автоматически промоутит одну из реплик. Для кворума нужно минимум 3 Sentinel'а. Альтернатива — Redis Cluster для шардирования."

## 8. Лицензия Redis: BSD → SSPL/RSAL → Valkey → снова открытый (AGPLv3)

### 🎯 Что спрашивают на интервью
> "Redis или Valkey — что вы используете и почему?"

### Простое объяснение
Это не праздный вопрос — за 2024-2025 годы Redis прошёл через реальную лицензионную драму, и senior backend-инженер должен уметь объяснить, что произошло и какие у этого практические последствия для выбора инфраструктуры.

### Хронология

```
До марта 2024:
  Redis — BSD-3-Clause (пермиссивная open source лицензия, OSI-approved)

Март 2024:
  Redis Inc. релицензирует Redis на dual SSPLv1 / RSALv2
  ("source-available", НЕ OSI-approved open source)
  → Причина (по заявлению компании): управляемые Redis-сервисы
    крупных облачных провайдеров монетизировали Redis, не
    возвращая вклад в разработку
  → Реакция сообщества и облачных провайдеров — резко негативная:
    много форков-протестов, недоверие к будущим лицензионным решениям

Март 2024 (тогда же):
  AWS, Google Cloud, Oracle и другие создают под эгидой Linux
  Foundation форк — Valkey — на последней BSD-версии Redis.
  Valkey остаётся полностью open source (BSD), drop-in совместим
  с Redis (тот же протокол, те же команды).
  → AWS ElastiCache/MemoryDB, Google Cloud Memorystore и другие
    managed-сервисы начинают предлагать Valkey по умолчанию или
    как равноценную альтернативу Redis.

Май 2025:
  Redis Inc. разворачивается на 180° и релицензирует Redis
  (начиная с Redis 8) под AGPLv3 — это снова OSI-approved open
  source. Официальная причина — вернуть доверие сообщества.
  → Но AGPL — это copyleft-лицензия с сетевым эффектом (network
    copyleft): если вы модифицируете Redis и предоставляете его
    как сервис (SaaS) третьим лицам, вы обязаны открыть исходники
    своих модификаций. Для компаний, которые просто используют
    Redis как зависимость (не форкают и не продают как сервис),
    AGPL практических ограничений не добавляет — но для облачных
    провайдеров, которые именно это и делают, AGPL так же
    неудобен, как и SSPL/RSAL.
```

### Практический вывод для senior-инженера

| Вопрос | Зачем важно |
|--------|-------------|
| Redis или Valkey у нас в проде? | Определяет, на какую лицензию/условия вы полагаетесь и какой вендор её поддерживает |
| Какая версия Redis? | До Redis 8 — SSPL/RSAL (не OSS); Redis 8+ — снова AGPLv3 (OSS, но с оговорками для SaaS) |
| Кто провайдер managed-сервиса? | AWS/GCP часто по умолчанию продвигают Valkey именно из-за этой истории; проверяйте, что конкретно поднимается под капотом |
| Форкаем/встраиваем ли мы Redis в свой продукт? | Если да — важна именно лицензия, а не просто "какая версия быстрее" |

На интервью не нужно перечислять месяцы наизусть — важно уметь объяснить: **был permissive BSD → стал source-available (SSPL/RSAL), что вызвало появление Valkey как открытого форка под крылом Linux Foundation и AWS/Google/Oracle → затем Redis Inc. вернулся к open source, но уже под AGPL, а не BSD**. И уметь аргументировать, какой вариант используется у вас и почему (доверие к вендору, поддержка облачного провайдера, лицензионные ограничения для вашего конкретного use case).

### 📝 Фраза для интервью
> "В марте 2024 Redis Inc. перешёл с BSD на dual SSPL/RSAL — source-available, не OSI-approved лицензии — что вызвало негативную реакцию сообщества и облачных провайдеров. В ответ AWS, Google Cloud, Oracle и другие под эгидой Linux Foundation создали Valkey — полностью открытый, drop-in совместимый форк на последней BSD-версии, и многие managed cloud-сервисы стали предлагать именно его. В мае 2025 Redis Inc. снова сменил лицензию — на этот раз на AGPLv3, вернувшись в open source, но AGPL — это copyleft с сетевым эффектом, неудобный прежде всего для тех, кто хочет предоставлять модифицированный Redis как сервис. На практике я всегда явно проверяю, что именно поднято в инфраструктуре — Redis или Valkey — и на какой лицензии, а не считаю это деталью, не влияющей на архитектурные решения."

## 9. Redis 8: нативный JSON и Search (RedisJSON и RediSearch в ядре)

### 🎯 Что спрашивают
> "Можно ли хранить и искать JSON-документы в Redis без отдельных модулей?"

### Простое объяснение
Раньше JSON-документы (RedisJSON) и полнотекстовый/векторный поиск (RediSearch) были отдельными модулями, которые нужно было ставить и подключать вручную — не все managed-сервисы их поддерживали. В Redis 8 эти возможности встроены в ядро — работают "из коробки", без дополнительной установки.

```bash
# Нативный JSON — без отдельного модуля
JSON.SET user:1 $ '{"name": "Иван", "age": 30, "tags": ["vip", "beta"]}'
JSON.GET user:1 $.name
JSON.SET user:1 $.age 31

# Нативный поиск/индексация — Query Engine (бывший RediSearch)
FT.CREATE idx:users ON JSON PREFIX 1 user: SCHEMA $.name AS name TEXT $.age AS age NUMERIC
FT.SEARCH idx:users "@age:[25 40]"
```

Что важно на интервью:
- Это снимает исторический аргумент "Redis — только key-value, для документов и поиска берите MongoDB/Elasticsearch" — для многих задач среднего масштаба Redis теперь закрывает и это, одним и тем же кластером.
- Не замена полноценному Elasticsearch/OpenSearch для сложного full-text ranking на больших объёмах — но для "искать по нескольким полям JSON-объекта, которые и так лежат в Redis" отдельная система больше не нужна.

### 📝 Фраза для интервью
> "В Redis 8 RedisJSON и RediSearch (Query Engine) — часть ядра, не отдельные модули, которые нужно ставить и поддерживать вручную. Это позволяет хранить JSON-документы нативно и строить по ним индексы/полнотекстовый поиск в том же Redis, где уже лежит кеш — не разворачивая под это отдельный Elasticsearch, если объём и сложность поиска не требуют специализированной системы."

## 10. Redis как vector database для RAG / AI

### 🎯 Что спрашивают
> "Можно ли использовать Redis для векторного поиска в RAG-пайплайне?"

### Простое объяснение
Тот же движок поиска (Query Engine, бывший RediSearch), что и для JSON-полей, поддерживает **векторные индексы** (HNSW и flat) и k-NN/range поиск по similarity — то есть Redis может выступать vector store для retrieval-augmented generation (подробнее про сам RAG-паттерн — в файле про Prompt Engineering).

```bash
FT.CREATE idx:docs ON JSON PREFIX 1 doc: SCHEMA
  $.text AS text TEXT
  $.embedding AS embedding VECTOR HNSW 6 TYPE FLOAT32 DIM 1536 DISTANCE_METRIC COSINE

FT.SEARCH idx:docs "*=>[KNN 5 @embedding $vec AS score]" PARAMS 2 vec "<binary-embedding>" SORTBY score
```

Когда это уместно:
- ✅ Проект уже использует Redis для кеша/сессий — не нужно поднимать отдельную vector DB (Pinecone, Weaviate, Qdrant) только ради RAG, особенно на среднем масштабе.
- ✅ Нужна низкая latency retrieval рядом с остальными hot-path данными в той же инфраструктуре.
- ❌ Очень большие корпуса (сотни миллионов+ векторов) со специализированными требованиями к индексации/фильтрации — там выделенная vector DB обычно даёт больше гибкости и предсказуемости по стоимости на масштабе.

### 📝 Фраза для интервью
> "Redis Query Engine поддерживает векторные индексы (HNSW), так что Redis можно использовать как vector store для RAG — храним embedding рядом с документом и делаем KNN-поиск по similarity. Это удобно, если Redis уже есть в инфраструктуре под кеш и сессии — не плодим отдельную vector DB ради одного use case. На действительно большом масштабе (сотни миллионов векторов, сложная фильтрация) специализированная vector DB всё ещё может быть оправданнее."

## 11. Redis Streams как альтернатива Kafka/RabbitMQ (для несложных задач)

### 🎯 Что спрашивают
> "Когда достаточно Redis Streams вместо полноценного Kafka/RabbitMQ?"

### Простое объяснение
Redis Streams — append-only log структура данных с consumer groups и acknowledgment (концептуально похоже на Kafka), уже встроенная в Redis. Если в проекте уже есть Redis, и нужна лёгкая очередь/event-log без разворачивания отдельного брокера — Streams закрывают немалую часть таких задач.

```bash
XADD orders '*' order_id 123 status created
XGROUP CREATE orders processors '$' MKSTREAM
XREADGROUP GROUP processors worker1 COUNT 10 STREAMS orders '>'
XACK orders processors 1234567-0
```

### Честно о том, где Streams НЕ достаточно

| Ограничение | Почему это важно |
|-------------|-------------------|
| Нет полноценной мульти-датацентровой репликации как у Kafka (geo-replication уровня Kafka MirrorMaker) | Для настоящего disaster recovery/multi-region event backbone Streams — не полная замена |
| Меньшая экосистема | Нет зрелого эквивалента Kafka Connect/Schema Registry/tiered storage; интеграций и tooling заметно меньше |
| Хранение ограничено памятью/диском одного Redis-инстанса (или кластера) | Kafka спроектирован для многотерабайтного долгоживущего лога с раздельным от памяти хранением; Streams — нет |
| Меньше готовых гарантий exactly-once semantics на больших пайплайнах | В Kafka это отдельная зрелая экосистема (transactional producers/consumers); в Redis Streams — вручную поверх ack/consumer groups |

### 📝 Фраза для интервью
> "Redis Streams — хороший выбор, если нужна лёгкая очередь или event-log, а Redis уже есть в инфраструктуре: консьюмер-группы, acknowledgment, replay из истории — всё это уже встроено, без отдельного брокера. Но это не замена Kafka для serious event streaming: нет сравнимой мульти-датацентровой репликации, экосистема (connectors, schema registry) значительно меньше, и хранение ограничено возможностями самого Redis-инстанса. Для внутренней очереди среднего масштаба — беру Streams; для durable event backbone на уровне компании с retention на недели/месяцы и multi-region — Kafka."

## 🎤 Частые вопросы на интервью

### "Почему Redis такой быстрый?"
> "Данные в памяти (не на диске), однопоточная модель без локов, оптимизированные структуры данных, эффективный протокол RESP."

### "Redis однопоточный. Это плохо?"
> "Для CPU-bound задач — да. Но Redis I/O-bound: основное время — сетевые операции. Один поток даёт простоту и отсутствие состояний гонки. При необходимости — масштабируем горизонтально (кластер)."

### "Когда НЕ использовать Redis?"
> "Когда данных больше, чем памяти. Когда нужны сложные запросы (JOIN). Когда важна строгая консистентность. Для основной базы данных (кроме специфичных случаев)."

### "Чем Redis отличается от Memcached?"
> "Redis: сложные структуры данных, персистентность, репликация, Pub/Sub. Memcached: только строки, проще, многопоточный. Для кеша оба подходят, но Redis универсальнее."

### "Как реализовать распределённую блокировку?"
> "SET lock:resource value NX EX 30 — атомарная установка с условием 'не существует'. NX = только если не существует, EX = TTL. Важно использовать уникальный value и проверять его при удалении."

### "Что такое Redis Cluster?"
> "Горизонтальное масштабирование Redis. Данные автоматически шардируются по хешу ключа на несколько узлов. Поддерживает репликацию и автоматический failover."

### "Чем Redis Cluster отличается от Sentinel?"
> "Sentinel — только HA (failover master→replica), данные на одном узле. Cluster — шардирование + HA, данные распределены по узлам. Sentinel проще, Cluster масштабируется."

### "Что такое Redis Streams?"
> "Append-only log структура данных. Похож на Kafka: consumer groups, acknowledgments, персистентность. Для надёжных очередей лучше чем Pub/Sub."

### "Как реализовать rate limiting?"
> "INCR + EXPIRE: увеличиваем счётчик, при первом увеличении ставим TTL. Если счётчик превышает лимит — отклоняем запрос. Более точный: sliding window через sorted sets."

### "Что такое Redis transactions?"
> "MULTI/EXEC — группа команд выполняется атомарно. Не настоящие транзакции: нет rollback, нет isolation. WATCH для оптимистичной блокировки."

### "Как найти все ключи по паттерну в production?"
> "НИКОГДА не KEYS — блокирует Redis! Только SCAN с курсором. SCAN итеративно обходит ключи, не блокируя сервер."

### "Что такое LRU eviction?"
> "Когда памяти не хватает, Redis удаляет ключи. maxmemory-policy: allkeys-lru (любые), volatile-lru (только с TTL), noeviction (отклонять записи)."

### "Как мониторить Redis?"
> "INFO команда для статистики. SLOWLOG для медленных запросов. redis-cli --stat для real-time. Внешние: Prometheus + redis_exporter."

### "Что такое HyperLogLog?"
> "Вероятностная структура для подсчёта уникальных элементов. Погрешность ~0.81%, но занимает всего 12KB независимо от количества элементов. PFADD/PFCOUNT."

### "Как Redis хранит данные?"
> "Всё в памяти как C структуры. Строки как SDS (simple dynamic strings), списки как quicklist, множества как intset или hashtable — в зависимости от размера данных."

### "Что такое Lua scripting в Redis?"
> "Выполнение Lua скриптов атомарно на сервере. Полезно для сложной логики, которую нельзя выразить одной командой. EVAL или зарегистрированные SCRIPT."

### "Redis vs DynamoDB/Cassandra?"
> "Redis — in-memory, микросекунды, ограничен памятью. DynamoDB/Cassandra — disk-based, миллисекунды, петабайты данных. Redis для кеша и hot data, NoSQL для основного storage."

### "Как бэкапить Redis?"
> "BGSAVE создаёт RDB snapshot в фоне. Копировать dump.rdb файлы. AOF файлы тоже можно бэкапить. Для больших данных — использовать реплику для бэкапа."

### "Redis vs Valkey — в чём разница и что использовать?"
> "Valkey — открытый (BSD) форк Redis, созданный под эгидой Linux Foundation в марте 2024 сразу после того, как Redis Inc. перешёл с BSD на source-available SSPL/RSAL; поддерживается AWS, Google Cloud, Oracle и другими, drop-in совместим с Redis (тот же протокол и команды). С мая 2025 сам Redis (начиная с версии 8) снова открытый — под AGPLv3. Что использовать — зависит от того, что предлагает ваш облачный провайдер по умолчанию, доверия к конкретному вендору и лицензионных требований вашего продукта (AGPL важен, если вы сами хотите форкать/предоставлять Redis как сервис). Я всегда явно проверяю, что именно поднято в проде — это не деталь, а часть архитектурного решения."

### "Что нового в Redis 8?"
> "AGPLv3-лицензия вместо SSPL/RSAL (снова open source), RedisJSON и RediSearch (Query Engine) встроены в ядро без отдельных модулей — нативные JSON-документы, полнотекстовый и векторный поиск из коробки."

### "Можно ли использовать Redis для RAG/AI как vector DB?"
> "Да — Query Engine Redis поддерживает векторные индексы (HNSW) и KNN-поиск по similarity. Удобно, если Redis уже есть в инфраструктуре под кеш/сессии — не нужно поднимать отдельную vector DB ради одного RAG-пайплайна. На очень большом масштабе специализированная vector DB может быть оправданнее."

### "Когда Redis Streams недостаточно и нужен Kafka?"
> "Когда нужна настоящая мульти-датацентровая репликация, долгий retention (недели/месяцы) большого объёма событий с раздельным от RAM хранением, зрелая экосистема коннекторов/schema registry, или строгие exactly-once гарантии на больших пайплайнах. Redis Streams хорош как лёгкая встроенная очередь поверх уже существующего Redis, но не спроектирован как durable event backbone уровня компании."
